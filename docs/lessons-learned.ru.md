# Lessons learned: Prefix Cache и двух-GPU runtime

Этот документ фиксирует подтверждённые результаты GP-24/24.1 и GP-25 на Experimental B для двух CMP50HX. Это эксплуатационная история конкретной модели, конфигурации и набора запросов, а не универсальная характеристика vLLM или Open WebUI. Числовые выборки и точные режимы сведены в [benchmarks.md](benchmarks.md), практическая модель Prefix Cache — в [prefix-cache.md](prefix-cache.md).

Метки доказательств: **CONFIRMED** — наблюдалось в конкретном тесте или подтверждено кодом; **DERIVED** — арифметическая оценка по записанным значениям; **NOT VERIFIED / UNKNOWN** — данных недостаточно. Все TTFT, PP и cache-hit числа относятся к указанной ниже конфигурации и не являются статистически значимыми без повторных прогонов.

## Prefix Cache: динамический system prompt

### Симптомы и первичная проверка

В четырёх последовательных запросах Open WebUI к одному чату промпты размером 15 838, 17 069, 18 392 и 19 666 токенов сообщали `cached_tokens=0`; TTFT составлял 18,79, 17,27, 18,67 и 20,19 секунды. В отдельной последовательности OpenCode к той же модели последующие ходы переиспользовали 14 832, 16 480 и 18 128 токенов, с TTFT 5,80, 4,98 и 4,69 секунды.

Сначала проверялись возможные причины на стороне vLLM, перестановка tool schemas и вытеснение KV. Для одного конкретного OWUI-наблюдения подтверждённым достаточным источником drift оказался system prompt: шаблон подставлял `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_DATETIME` и `CURRENT_WEEKDAY` при каждом запросе. Middleware заново собирал system message для следующего запроса.

Сохранённая system-инструкция содержала 7 837 символов / 2 146 токенов. В безопасном system-only сравнении вариантов с интервалом 60 секунд первая разница token IDs была на позиции 72. Production cache block этого профиля — 1 648 токенов. Общий префикс короче одного полного блока не даёт ни одного полного блока для переиспользования. Prefix Cache ищет совпадающую начальную последовательность блоков, а не одинаковый суффикс в произвольном месте промпта; раннее отличие поэтому лишает повтора и последующие блоки.

Это локализует источник прежнего miss в конкретной конфигурации OWUI. Это **не** доказывает upstream-регрессию между Open WebUI 0.12 и 0.13.3: проверенный `prompt_template()` / `resolve_system_prompt()` путь подстановки времени был одинаков в обеих версиях. Почему старый конфиг 0.12 не показывал тот же симптом, остаётся **UNKNOWN**. Полные исторические token IDs запроса, весь набор тогдашних 64 tool schemas и точный исторический LCP не сохранялись.

### Исправление и наблюдение после GP-25.2

GP-25.2 заменил только динамический Time and knowledge блок четырёх используемых model records и трёх Skills: начальный prompt стал статическим, актуальное время запрашивается только при необходимости. Уникальные инструкции моделей и Skills сохранялись. Backend и Docker image не менялись. Содержимое приватных инструкций в этот публичный документ не включено.

Одна последующая синтетическая OWUI последовательность дала:

| Ход | Вход, токенов | Cached | TTFT |
|---:|---:|---:|---:|
| 1 | 15 398 | 0 | 18,10 с |
| 2 | 16 096 | 13 184 | 3,15 с |
| 3 | 16 797 | 13 184 | 3,85 с |
| 4 | 17 537 | 14 832 | 2,88 с |

Дополнительное пользовательское использование после применения GP-25.2 также сообщало ненулевые cache hits на всех четырёх наблюдавшихся ходах: 13 184, 13 184, 14 832 и 14 832 при размере входа 15 431–18 794 токена. Эти наблюдения подтверждают повторное использование cache в тех последовательностях; исходные prompts не были побайтово повторены, поэтому это не строгий A/B replay и не формальный benchmark.

Backend-патч GP-25.1 с conversation-scoped clock snapshot и 30-минутным TTL для данного набора конфигураций не понадобился: динамическое время удалено из начала prompt на уровне записей конфигурации. Patch остаётся отдельным экспериментальным candidate, не развёрнутым и не являющимся частью основного исправления.

## Hybrid KV residency при DFlash2 K=7

Скаляр `GPU KV cache size` не описывает все независимые cache groups. В production K7 после GP-21.3 target full-attention group имела 151 блок всего, 150 usable и размер страницы 1 648 токенов; пять независимых draft groups имели собственные лимиты. Startup headline составлял 247 398 токенов.

Одна последовательность 98 304 токена требует около 60 страниц full-attention (`ceil(98 304 / 1 648) = 60`). Три уникальных последовательности такой длины потребовали бы порядка 180 страниц, что превышает 150 usable attention blocks, даже до учёта влияния остальных hybrid groups. Это объясняет, почему три полностью резидентных 96K-контекста не гарантированы одновременно; вывод относится к residency, а не к максимальной длине отдельного запроса.

В pressure-тесте точный повтор одного 98 304-токенного запроса удержал 51 088 cached tokens и пересчитал 47 216. TTFT был около 70,18 с. Такой TTFT совместим с пересчётом существенной части префикса и вытеснением при ограниченной residency; сам по себе он не доказывает неисправность hash lookup или Prefix Cache. В отдельном низком давлении повтор K7-контекста удерживал 95 584 токена.

Не переносите число `247 398` на независимые cache groups как общий резерв: admission зависит от group-specific capacities, alignment, Mamba/DFlash reservations, output growth и одновременной нагрузки.

## Стабильность tool schemas

В синтетическом тесте с 6 733-токенным общим префиксом изменение порядка первых двух gateway-assembled tool schemas уменьшило наблюдаемый hit с 4 944 до 0; при возврате исходного порядка hit 4 944 восстановился. В этом же тесте TTFT вырос примерно с 1,75 до 6,53 с. Это подтверждает чувствительность конкретного запроса к сериализованному порядку схем, но не объясняет автоматически все production misses.

OpenCode передаёт явный массив инструментов; исследованный 12-tool порядок оставался неизменным, `execute` был последним. Open WebUI формирует собственные native/MCP/terminal tool sets через gateway; порядок собранного набора не имел такого же явного клиентского контракта. Локальный GP-25 кандидат канонизирует только gateway-assembled порядок и оставляет явный порядок клиента без изменений. Его четыре коммита и 22 целевых теста сохранены локально, но патч **не развёрнут** и не является исправлением причины динамического system prompt.

## vLLM A/B: что показал и чего не показал

GP-24.1 сопоставил архивную A и B common на одинаковых весах, железе и token-ID corpus в no-spec профиле: TP2, FP8 target KV, context 200 000, два scheduler sequences, 2 560 batched tokens, Mamba align, Prefix Cache ON, CUDA Graph capture size 4, Custom AllReduce OFF. На четырёх размерах одного прохода B common показал более высокую cold Physical PP и меньший cold/warm TTFT. Полная таблица и ограничения находятся в [benchmarks.md](benchmarks.md).

Это не сравнение production K7: конфигурации различались по speculative decoding, KV-pool sizing, context, батчингу и graph capture. В отдельном одном запросе 4K→128 no-spec B common показал клиентские 13,83 tok/s против 33,20 tok/s у A; production B K7 для той же формы decode ранее показывала около 103,08 tok/s. Этот единичный аномальный результат не повторялся в достаточном объёме; причина **UNKNOWN**. Не приписывайте его DFlash2 или scheduler без повторяемого matched test.

## Другие подтверждённые эксплуатационные уроки

### CMP50HX, драйвер, PCIe и TP2

В hardware snapshot от 11 ноября зафиксированы драйверный модуль 610.43.03 на Linux kernel 6.8.0-137 и negotiated PCIe links Gen2 x16/x16 для GPU0/1 и x4 для GPU2. Production runtime использовал TP2 на GPU0/1. Эти наблюдения не устанавливают содержимое unlock patchset, производительность P2P, BAR1 aperture или действующие настройки ReBAR. PCIe link, CMP compute unlock, ReBAR/BAR1, CUDA P2P и NCCL transport — разные механизмы; нельзя подтверждать один по другому. Текущая причинная связь этих параметров с Prefix Cache misses не обнаружена.

### CUDA, FlashInfer и Triton

При первом inference в изолированной копии A FlashInfer JIT не нашёл `nvcc`: сокращённый launcher не передавал штатные `CUDA_HOME` и toolkit PATH. После восстановления нужного окружения candidate compile прошёл с CUDA 12.8 и GCC 13. Это был дефект launcher environment, а не доказанная несовместимость версии FlashInfer с SM75. A и B использовали разные Python/Torch/CUDA/Triton/FlashInfer стеки; универсальная матрица их взаимной совместимости не проверена. Сохраняйте исходный launcher и фиксируйте compile toolchain отдельно от пакетов Python.

### RAM, диск и resource guards

Во время загрузки checkpoint в A наблюдались суммарное чтение около 19,55 GB, worker RSS порядка 3,5 GiB на процесс и cgroup около 12,46 GB. В A/B окне I/O PSI full avg10 доходил до 82,77%, memory PSI — до 50,96%; минимальная MemAvailable в измеренном окне была около 6,67 GiB, OOM не было. На дисках во время эксперимента оставалось около 17,73 GiB NVMe и 20,54 GiB SSD. Guard приостанавливал работу при устойчивом resource pressure и недостаточном запасе на безопасное возобновление.

Эти данные подтверждают нагрузку на чтение/хранилище в данном эксперименте, но **не** доказывают причину исторических перезагрузок 10 ноября. Для RCA нужно сопоставлять RSS/PSS/cgroup, чтение checkpoint, MemAvailable, memory и I/O PSI, swap-in/out и OOM events по времени. Ни заполненный swap, ни единичный PSI пик сами по себе не устанавливают причину.

### Cached PP — не физическая скорость prefill

В старом графике Monitor поле, названное Cached PP, могло представлять rate агрегированного `prefix_cache_hits_total` за scrape interval. Этот счётчик отражает число повторно использованных token positions за интервал, а не количество prompt tokens, физически вычисленных GPU за секунду. Из-за этого между запросами могли возникать нули и пики, которые ошибочно выглядели как PP. GP-20 добавил отдельный live counter физических prefill positions после успешного model-runner output; cache hits, external KV, decode и speculative verification в нём исключены. Request-level `cached_tokens` и aggregate cache counters нельзя подменять друг другом.

### Downstream source и контейнерные образы

Production Open WebUI содержала локальные downstream patches, поэтому upstream image/tag не был эквивалентом production image. При пересоздании контейнера необходимо фиксировать image digest, Compose, mounts, env, volume/SQLite backup и версионированные patch sources; rollback к старому image не должен восстанавливать старую SQLite целиком поверх новых чатов.

Для vLLM public repository хранит восстановленный Experimental B snapshot и последующие downstream commits. GPU runtime validation на двух CMP50HX и чистая native build/install непосредственно из опубликованного GitHub checkout — разные критерии. Clean build из публичного checkout остаётся **NOT VERIFIED**; это не означает, что Experimental B не проходил GPU runtime tests. В релиз не включены production weights, private launcher, unit files, prompts, пользовательские запросы или host addresses.

## Практический чек-лист расследования miss

1. Зафиксировать per-request `prompt_tokens`, `cached_tokens`, фактически computed tokens, TTFT и runtime profile.
2. Без raw prompt сравнить token IDs или HMAC/fingerprints по последовательным блокам и найти первый divergence.
3. Проверить, начинается ли divergence раньше первого полного cache block; проверить системные инструкции, порядок tool schemas и chat-template version.
4. Отдельно проверить residency/eviction: prompt мог совпасть, но блок уже вытеснен из ограниченного hybrid pool.
5. Только после этого классифицировать miss как нестабильность payload, eviction, несовместимость формата или ошибку metrics.
6. Сохранять точные profile/build hashes; любой A/B менять только один фактор и не смешивать no-spec common профиль с production K7.
